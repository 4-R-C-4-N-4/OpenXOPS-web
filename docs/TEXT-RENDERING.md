# Japanese text rendering (CP932 + Shinonome bitmap font)

## Problem

`D3DGraphics::Draw2DMSFontText` previously replaced every CP932 double-byte
character with `?`, because the browser build has no Windows GDI text
rendering. Menus and briefings that use Japanese text were unreadable.
`Draw2DMSFontTextCenter` also computed centering width from
`StrMaxLineLen()`, a raw byte-length count, so mixed half/full-width lines
were off-center.

## Design

`src/platform/text/`:

- `text.h` / `text.cpp`: `cp932_decode()` decodes one CP932 (Windows-31J)
  character per call, returning the Unicode codepoint and bytes consumed.
  Malformed or truncated lead bytes consume only the bytes actually present
  and report failure (caller substitutes U+FFFD and resynchronises on the
  next byte) instead of reading past the end of the buffer.
- `cp932_table.inc`: a generated single/double-byte -> Unicode lookup table.
  Generated by `tools/fonts/gen_cp932.py` from Python's built-in `cp932`
  codec (not hand-authored, not copied from any third-party source).
- `font_atlas.inc`: a glyph bitmap atlas (12x12 half-width / 16x16 full-width
  dot patterns) in the Shinonome public-domain bitmap font style. See
  `assets/fonts/README.md` and `NOTICE.md` for provenance and license.
  **Coverage today is Latin-1 Supplement only** — hiragana, katakana and
  kanji glyphs are not yet included; see "Known limitation" below.
- `text_measure()` computes the exact pixel width/height a string will
  render at (accounting for mixed half-width ASCII/kana and full-width
  kanji glyphs) without allocating or rendering pixels — used for centering.
- `text_bitmap()` renders a CP932 byte string to a tightly packed RGBA8
  buffer, one opaque white glyph per character on a transparent background.
  Codepoints with no glyph in the compact atlas draw a visible outline box
  rather than silently vanishing, so missing coverage is obvious instead of
  invisible.

`D3DGraphics::Draw2DMSFontText` (in `d3dgraphics-portable.cpp`) calls
`text_bitmap()`, uploads the result as a one-off GL texture, and draws it as
a single textured quad tinted by the requested color — reusing the existing
`Start2DRender()`/`End2DRender()` GL state setup and the same vertex/color
array drawing path as `Draw2DTextureFontText()`, so alpha blending and 2D
projection state are unchanged. The texture is deleted after the draw call
(this path is already documented as "very slow, call sparingly" upstream)
and the previously bound texture-font texture, if any, is restored.

`D3DGraphics::Draw2DMSFontTextCenter` now calls `text_measure()` to get the
real rendered pixel width (half-width run = 9px at logical 640x480 scale,
full-width run = 18px) instead of `strlen()*halfwidth`, so mixed ASCII/kana
and kanji lines center correctly.

ASCII-only `Draw2DTextureFontText*` (the HUD texture-font path) is untouched.

## Kana/kanji glyph coverage

`font_atlas.inc` now contains real Shinonome glyph bitmaps for hiragana,
katakana, full-width symbols and JIS X 0208 level-1/level-2 kanji
(~6,900 codepoints), plus half-width katakana, generated by
`tools/fonts/gen_font_atlas.py` from the upstream `shnmk16.bdf` (16x16) and
`shnm8x16r.bdf` (8x16) BDF fonts in the public-domain `shinonome-0.9.11`
release (see `assets/fonts/README.md` for the pinned URL/SHA-256 and
`NOTICE.md` for the license summary). The existing hand-authored Latin-1
Supplement entries are untouched. CP932 decoding is complete and correct for
the full Windows-31J byte repertoire, and the GL rendering/texture/centering
pipeline is verified working end-to-end: loading a real `xops096.zip` and
opening a mission briefing now visibly decodes CP932 mission text as
legible hiragana/katakana/kanji glyphs instead of outline-box placeholders.
Any codepoint that is genuinely outside JIS X 0208 (e.g. vendor/NEC-row
extensions, or private-use CP932 bytes) still falls back to a visible
outline box rather than being silently dropped.

## Testing

`tools/tests/test_text_rendering.py` builds and runs a small C++ harness
(`tests/text/cp932_harness.cpp`) against `cp932_decode`/`text_measure`/
`text_bitmap` directly (no browser needed) and checks:

- ASCII round-trips unchanged.
- Known CP932 double-byte sequences decode to the expected Unicode
  codepoints (hiragana/katakana/kanji samples).
- Truncated/malformed lead and trail bytes fail cleanly without reading out
  of bounds (consumed-byte count never exceeds the remaining buffer).
- `text_measure()` width for a half-width-only string, a full-width-only
  string, and a mixed string matches the expected half/full width sum.
- `text_bitmap()` returns a correctly sized non-empty buffer and actually
  paints at least one opaque pixel for a known glyph.

Full verification also requires a WASM build and loading a real
`xops096.zip` in the browser to visually confirm menu/briefing Japanese text
renders (see `docs/FINAL-POLISH.md`).
